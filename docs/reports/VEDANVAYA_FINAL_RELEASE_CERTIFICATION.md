### The one MISLEADING — Q38, "Who are the Maruts?"

Returned to the reader as `SUPPORTED` / `STRONG` with no quantitative caveat. It makes two
corpus-level ranking claims that appear in no cited item and that the live graph
contradicts:

1. *"They are the most widely mentioned deity group in the corpus"* — the Maruts total 560
   verses under `MENTIONS_DEVATA` and rank **third** among plural deities, behind
   `āpaḥ` (the Waters) at 761 and `aśvinau` at 626.
2. *"In the Rigveda they also receive the largest number of hymn-level dedications
   (HAS_DEVATA), totalling 428 verses"* — 428 is rank **six**, behind Indra 2,869, Agni
   1,988, Soma Pavamana 1,087, the All-Gods 805 and the Aśvins 631.

The packet holds only the Maruts' own rows and ranks nothing; the graph carries no
deity-group typing at all. **Every figure in those sentences is real and correctly cited** —
560's components and 428 both come straight from the packet — so the citation audit, the
figure check and the quantitative validator all pass. The unsupported tokens are the words
*most widely* and *largest*.

This is the same shape as the Q02 `all ten mandalas` defect, where "every figure in the
sentence was real and correctly cited, so the citation audit passed and the figure check
passed; the unsupported token was the word 'ten'." The universal rule shipped for that case
does not reach a comparative superlative, because the validator scopes to integers a
sentence cites and a superlative carries no comparison figure to test against.

Two things narrow it. Retrieval is not implicated: all 60 packets replayed identically and
nothing was fabricated. And the frozen run's answer to this same question contained
neither superlative, so this is a re-ask regression in synthesis, not a standing retrieval
defect. Q02 in this run makes the identical "largest number of hymn-level dedications"
claim about **Indra**, where it is true (2,869, rank 1) — the model reuses the phrase
regardless of subject.

**Smallest remediation.** Q38 alone, by the documented `scripts/grade_ask_delta.py`
procedure: fix the concrete defect, re-ask the one question at the new commit, compose
59 + 1 with per-question provenance, and leave the frozen 60 as immutable evidence.
Re-asking requires live provider quota, which this pass did not spend.

### A second finding this pass had to fix before it could measure

The first accounting run showed **six** failures, not one. Two were the stale census pins
above. The other four were in `tests/llm`, and all four had one cause.

About two dozen one-off scripts under `data/staging/**` call `load_dotenv` on an absolute
path at *import* time, and several tests import one of them with `spec_from_file_location`
to reach a single pure function. Importing is enough: the developer's real
`VEDAGRAPH_LLM_API_KEY` lands in `os.environ` and stays there for the rest of the session.
`vedagraph.llm.credentials.load_credential_slots` reads `os.environ` directly and
deliberately — a credential slot is a deployment fact, not a settings field — so that key
becomes a configured slot. `get_llm_provider` then stops raising on a missing key and
`/ask/health` answers 200 where it must answer 503.

Which tests fail depends on collection order, so the suite is green on a machine with no
`.env` and red on a developer's. The ordering that failed loudly is the lucky one. The
inverse is the hazard: **a guard that must fire when no key is configured cannot be
trusted while any earlier test can quietly configure one**, and four of the tests this
silently disarms are the ones asserting that a key is absent — including the secret-safety
test for `/ask/health`.

Fixed with one autouse fixture in `tests/conftest.py` that restores credential-shaped
environment variables against a **session-scoped** baseline. Session scope is the point: a
per-test snapshot is taken too late when the leak happens inside a module-scoped fixture,
because higher-scoped fixtures are set up first, so the per-test "before" already contains
the leaked key and would faithfully restore it. That was tried first and did not hold.
The sealed staging artifacts were not edited.
